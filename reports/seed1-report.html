Seed 1 report · scenario bank-cobol-springboot-v2 · runs of 11–12 Nov 2026

Does Living Memory make an AI engineering team better?

We simulated a 14-person bank modernization team made entirely of AI coding agents and ran the same four-sprint project three times: with no memory, with Claude Code's built-in memory, and with Living Memory. In this single run per setup, Living Memory did not produce better work. Its agents were a little cheaper and took fewer steps, but they scored lowest on the hidden work tests and roughly tied on a knowledge quiz. Living Memory itself behaved much better than in our first simulation: agents kept their notes current and every agent but one kept a project brief. One run per setup is too few to call a winner, so read every difference below as a hint, not a verdict.

1 · Background

What Living Memory is, and why we tested it this way

AI coding agents forget everything between sessions. Tools such as Claude Code start each session with an empty head. Whatever an agent learned yesterday (a decision, a trap in the build, who owns which module) is gone today unless someone wrote it down where the agent will look.

Living Memory is a memory add-on for these agents. It is a small program that keeps a personal store of short notes (decisions, rules, gotchas, a map of the codebase, a brief of the project) and plugs into the agent through hooks, small scripts the agent runs automatically at set moments. When a session starts or the user asks something, Living Memory looks up relevant notes and puts them in front of the agent. When the agent is about to finish, a Stop reminder can ask it to save anything worth keeping before it stops.

Testing memory with one person is easy; testing it in a team is not. The real question is whether memory helps in the messy setting of a company: many people, decisions that change, colleagues who leave, information scattered across a code repository, a ticket tracker, a wiki and chat. So we built a simulator that plays a whole team, with every team member an independent AI agent with its own memory.

The first simulation exposed big gaps

The first run (11 Nov, a 12-agent team, the older Living Memory) showed the plumbing worked flawlessly, but memory held little of what the team knew. With only their memory to go on, agents answered 6% of the questions they should have known. Of 72 missed answers, 53 were facts never saved at all, because Living Memory's instructions told agents to skip anything already written in the code or docs. Notes also went stale: the architect's own codebase map still described the money type it had replaced, and across 62 work sessions agents updated notes only 5 times.

We then rebuilt parts of Living Memory

Three rounds of changes were made, reviewed and installed before this test (called phases 1 to 3):

  • Capture: agents are now told to save the load-bearing part of everything, including what docs, tickets and commits record, as a short note that points to the source. The Stop reminder now blocks once when a decision document was edited, a decision arrived in the conversation, or a project brief is missing. Each project gets one living project brief: goals, owners, current phase, blockers, key decisions.
  • Retrieval: long task prompts are searched in pieces, so the actual assignment is not drowned by boilerplate; notes about known traps are shown at session start; notes about a command are shown when the agent is about to run that command.
  • Currency: codebase maps are keyed to the repository rather than the folder, and a map is flagged as stale when files it describes change; notes that state a guess are flagged as a hypothesis.

Three further phases (a searchable index of all project documents and code, document digests, and wiki connectors) are built but were not installed, so they were not part of this test.

2 · The simulated project

Project LIGHTHOUSE at Harbor Point Savings & Trust

The fictional bank Harbor Point runs its nightly batch (accounts, transfers, daily interest, month-end posting, fees, statements) on COBOL, a decades-old mainframe language. Project LIGHTHOUSE ports it to Java 21 and Spring Boot 3, the stack many real banks use. The new system must reproduce the old one's output exactly (parity) on 59 days of captured real-world-style data, except where the business has approved a change.

The team works for four two-week sprints, compressed into three working days each. Every working day is a fresh session for every agent, so nothing carries over unless it was written down: in the repository, the tracker, the wiki, chat, or (in arm C) Living Memory.

How one working day runs

Leads and analysts work (wave 1)→ Merge + build and test (CI)→ Developers and migration (wave 2)→ Merge + CI→ QA, security, ops (wave 3)→ Merge + CI

Up to four agents work at once, each in its own copy of the repository. A bot merges their work and runs the build and tests after each wave, and posts CI failures to the team chat. Each agent gets a short prompt in an engineer's voice, such as "Back on month-end posting today. Anything changed overnight? Then carry on." Nobody is told what to remember.

What makes it realistic

  • Knowledge lives in many places. The repository holds code and docs; the ticket tracker, the wiki and team chat live outside it, as in a real company.
  • Business colleagues who only answer when asked. Six simulated non-engineers (head of retail deposits, product committee, compliance, the CFO's office and others) know key facts and reveal them only if an engineer asks them in chat.
  • Natural traps. A stale product catalogue on the wiki still lists the old $35 fee. A workstation git hook rejects commits whose message doesn't start with a ticket key. CI runs lint rules that the local build does not.
  • People change. Two engineers leave mid-project and hand over to newcomers; one goes on vacation and a colleague covers.
  • Decisions change. The money format chosen in sprint 1 is overruled in sprint 3, and an approved fee change is amended in sprint 4.

4 · How we measured

Hidden work tests, a quiz, and the bookkeeping

Work tests (the main measure). In sprint 4, nine ordinary-looking tasks were given to specific agents. Each one quietly depends on something the team learned earlier, often from a colleague or a decision that is not in the code. A test is scored from 0 to 1 against a hidden checklist, using the agent's reply, the code it committed, and the tracker and wiki pages it changed. The agents were never told they were being tested.

Knowledge quiz. After sprint 4 every agent answered 17 questions about the project (rules, decisions, who owns what, the incident, the project phase). Each question is tied to one of 15 facts with a known correct answer. Scores count only the agents who should know that fact from their role or from something they were told (the "should-know" score). Two versions:

  • With repo access, in every arm: the agent may use the repository, tracker, wiki and its memory. This is how people actually work, so it is the fairer comparison.
  • Memory only, in arm C: file and shell reads are blocked, so only Living Memory can answer. This isolates what memory alone holds.

Grading. Answers and work-test checklists are graded by a separate AI judge (Claude Sonnet, no tools) against the answer key, as correct, partial, stale (gives the outdated answer), wrong or unknown. Correct counts 1 and partial counts 0.5. Some work-test items are plain text-pattern checks. Before trusting the judge, we audited it on 25 answers with known grades: it agreed on 96%, never accepted a wrong or stale answer, and never rejected a right one. The audit result was identical in all three runs.

Bookkeeping. The simulator also records cost, steps (turns) and tool calls per session; build health; whether agents repeated a planted mistake after learning about it; the content and history of every memory store; and how long each Living Memory hook took.

6 · Inside Living Memory

How the agents actually used memory

Much more was saved, and it was kept current. The 14 stores ended with 95 active notes (26 decisions, 23 knowledge notes, 14 codebase maps, 13 project briefs, 10 risks, 7 status notes, 4 bugs, 3 context notes). Agents updated notes 117 times and marked 5 as replaced by newer ones. In the first simulation the figures were 32 notes, 5 updates and 0 replacements.

Project briefs took hold. 13 of 14 agents kept a brief; only the architect did not. Briefs carried the project phase and ownership, which is where arm C beat the other arms on the quiz.

Handovers worked. Chen exported 5 notes to Lucas and Raj exported 7 to Nadia; both imported with no conflicts.

Usage was steady. Agents made 329 memory calls, about 2 per work session, with zero errors. The Stop reminder made an agent continue to save something 55 times across the run.

But memory alone still answers less than a quarter. In the memory-only quiz, of 128 should-know answers:

Answered50
Never saved36
Saved, not found35
Outdated note7

"Answered" includes partial answers, which is why the score is 0.227 rather than 39%. The two failure causes are now about equal: facts nobody saved, and facts that were saved but the agent's search did not surface. Incident INC-0042 is the clearest case: every agent who should know it had it in their store, and none answered it from memory.

Pointers to documents: 12 of the 19 decision documents and handoffs had a note in their author's store pointing to them (63%). The architect saved no pointer to its first two ADRs.

Speed: Living Memory added no visible time. Its sessions averaged 122 seconds against 131 (A0) and 128 (A1). Hook timings (median / 95th percentile): before each tool 31 / 59 ms; on each prompt 218 / 323 ms; at stop 49 / 183 ms; at session start 578 / 770 ms, which includes loading the search model.

Built-in memory (A1) barely engaged. Over 142 work sessions, Claude Code's own memory saved a single note: an analyst's status note from sprint 1. In practice A1 was a second no-memory run, so its differences from A0 show how much two runs of the same setup can differ by chance.

7 · What it means

Findings

Inconclusive

No setup clearly did better work

The spread between arms (0.43 to 0.56 on work tests, 0.70 to 0.72 on the quiz) is about the size of one or two tests flipping. A1, which barely used memory, differs from A0 by 0.07 on the work tests; C differs by 0.13. More runs per arm are needed before claiming any difference in quality.

Improved

The remediation fixed what the first simulation found

Agents now save decisions and context, keep notes current (117 updates against 5), keep a project brief, and hand knowledge over cleanly. The memory-only score rose from 6% to 23%, though on a different, harder scenario, so the comparison is rough.

Promising

Memory helped where the repository is weakest

Questions about people and project state (who owned what, who owns it now, what phase we are in) are where arm C scored highest. These facts change over time and are scattered across chat and tickets, which is exactly the job of the project brief.

Efficient

Living Memory was slightly cheaper, not slower

C used fewer steps per task (10.3 against 12.0 on the work tests) and cost less per session, despite running the memory hooks. An earlier impression that it ran three times slower was a measuring mistake (see below).

Risk

A team record can be wrong, and memory may reinforce it

C's team recorded the fee cap as unconfirmed and every agent repeated that, even after seeing the cap in the repository. Memory makes a team consistent; if the shared belief is wrong, it can make it consistently wrong. This needs watching in future runs.

Gap

Retrieval is now the bottleneck as much as capture

35 should-know facts were in an agent's own store but not found when asked. Better search over notes, and the document index built in phases 4 to 6, target this directly.

Bug

The Stop reminder can bury the agent's answer

When the reminder fires after an agent has answered, the agent's last message becomes "I saved a note; my answers are above". Any script or tool that reads only the last message gets the wrong text. It also fires in question-only sessions, asking for a codebase map where nothing was explored. Living Memory should handle non-interactive sessions differently.

8 · Measurement problems

Two problems we found in our own measuring, and fixed

Answers hidden behind memory housekeeping. The first scoring of arm C read only each agent's last message. Because of the Stop reminder bug above, 8 of 14 repo-quiz answer sheets and 6 of 9 work-test replies were read as "I saved a note" instead of the real answer. The quiz score first came out as 0.348, which looked like a collapse. We changed the simulator to read the agent's real answer (the text written before the memory saving at the end) and regraded arm C from its saved transcripts. No agent was rerun. Arms A0 and A1 have no Stop reminder; their evidence was byte-for-byte the same under the new reader, so their scores stand. Work tests whose evidence did not change kept their original grade.

Sessions that stayed open after finishing. Some agents started a background command (a wait loop, a build watcher) and finished their work, but the session stayed alive until that command's own time limit, up to 19 minutes. Each wave waits for its slowest agent, so these delays added up in every arm: 12, 9 and 32 minutes of idle time in A0, A1 and C. The simulator now ends a session 30 seconds after the agent's final answer. Every run took about three hours regardless of memory.

9 · Limits

How far to trust this

  • One run per setup. AI agents behave differently each time they run, and the three planned repeats per arm were cancelled. Differences of 0.1 on the work tests are within what chance alone produces.
  • Nine work tests and fifteen facts. Small samples, chosen by us. A different set of tests could rank the arms differently.
  • An AI judge grades the work. It passed its audit (96% agreement, no false passes), but it can still be strict or lenient on borderline cases.
  • Cheap, fast models at low effort. Stronger models or higher effort might use memory very differently.
  • A compressed project. Four sprints of three days each is a short project. Memory should matter more over months, as people forget and teams turn over; this test cannot show that.
  • Partial Living Memory. Only phases 1 to 3 were installed. The document index and digests, aimed at the retrieval gap, were not tested.
  • Arm C was scored after a fix. The regrading followed a fixed rule and changed only how the answers were read, but it was done after we had seen the first numbers.

11 · Next steps

What would settle the question

  1. Fix the Stop reminder for non-interactive sessions, so it never replaces an agent's answer and doesn't fire in question-only sessions.
  2. Install phases 4 to 6 (document index, digests, wiki connectors), which target the "saved but not found" gap, then test a fresh agent that only has the indexed project to answer from.
  3. Run more repeats when a firm answer matters: at least three runs per arm, now roughly 2.5 hours and $17 each with the simulator fixes.
  4. Look into the fee-cap judgment: whether memory notes or the briefs carried "unconfirmed, do not build" from one agent to the rest of the team.
Glossary

Terms used in this report

Agent
An AI model (here Claude) working as a software engineer: it reads files, runs commands and writes code by itself.
Session
One sitting of one agent, here one working day. Each session starts with no memory of earlier ones.
Living Memory
The memory add-on being tested. It keeps short notes per person and shows relevant ones to the agent automatically.
Store
One person's collection of Living Memory notes. Each agent had its own private store.
Hook
A small script the agent's tool runs at fixed moments (session start, each prompt, before a command, at the end), through which Living Memory reads and suggests notes.
Stop reminder
A hook that, when an agent is about to finish, may ask it once to save something important first.
Codebase map
A note describing how a repository is laid out and built, so the next session need not re-explore it.
Project brief
A note per project with goals, owners, current phase, blockers and key decisions, kept up to date.
Arm
One of the setups being compared (A0, A1, C).
Seed
One repeat of a run. AI agents behave differently each time, so repeats show how much is luck. This report covers seed 1 only.
Work test (probe)
An ordinary-looking task that secretly needs earlier knowledge, scored against a hidden checklist.
Should-know
A fact an agent ought to know from its role or from something it was told; quiz scores count only these.
Parity
The new system producing exactly the same results as the old one on the same input.
CI
Continuous integration: the automatic build and test run after work is merged.
ADR
Architecture decision record: a short document recording a technical decision and why.
COBOL
A programming language from 1959 still running much of the world's core banking.
